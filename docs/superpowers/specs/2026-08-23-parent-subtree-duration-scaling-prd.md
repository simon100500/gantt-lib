# PRD: Пропорциональное сжатие и растяжение поддерева задач

Дата: 2026-08-23  
Статус: **FUTURE — согласованный дизайн, не реализовано**  
Целевая версия: не назначена  
Область: `gantt-lib/core/scheduling`  
UI и интеграция GetGantt: отдельный будущий этап

> Этот документ описывает будущую возможность библиотеки. Наличие документа не
> означает, что API уже экспортируется или что родительские задачи можно изменять
> через текущий UI.

## 1. Для кого написан документ

Основной читатель — инженер или AI-агент, который впервые видит задачу и должен
реализовать её в `gantt-lib` без доступа к обсуждению, на котором были приняты
решения.

После чтения он должен суметь:

1. обновить контракты scheduling-core;
2. реализовать чистую headless-операцию масштабирования поддерева;
3. добавить публичные типы и экспорт;
4. доказать тестами точное, атомарное и детерминированное поведение;
5. не смешать библиотечную математику с продуктовой политикой GetGantt.

## 2. Проблема пользователя

Родительская задача является вычисляемой обёрткой над потомками. Её даты равны
минимальной дате начала и максимальной дате окончания дочерних работ. Поэтому
пользователь не может просто изменить длительность этапа.

На реальном графике под родителем может находиться 100 и более работ. Если этап
занимает 120 дней, а его требуется уложить в 90, ручное изменение каждой работы
неприемлемо.

Нужна одна операция:

> Пользователь меняет длительность родительского этапа, например с 20 до 30 дней,
> а библиотека пропорционально перестраивает все работы под ним.

Главный пользовательский приоритет — общий срок или конечная дата этапа.
Однодневная разница внутри отдельных работ менее важна, чем точное попадание в
заданный диапазон.

## 3. Цель

Добавить в headless scheduling-core чистую операцию, которая:

- принимает родительскую задачу, целевую длительность и snapshot проекта;
- пропорционально изменяет длительности листовых работ;
- сохраняет технологические лаги, пока это возможно;
- при дальнейшем сжатии уменьшает разрешённые лаги;
- масштабирует временное положение независимых веток;
- пересчитывает всех вложенных родителей снизу вверх;
- точно попадает в целевую длительность, если она достижима;
- при недостижимом запросе применяет минимально достижимую длительность и
  возвращает машинно-читаемое предупреждение;
- никогда не мутирует входной snapshot;
- возвращает один атомарный batch изменений.

## 4. Не-цели первой реализации

В эту работу не входят:

- разрешение resize родительского бара мышью;
- поле длительности и системные уведомления в GetGantt;
- persistence, optimistic concurrency, Undo/Redo и receipts;
- автоматический выбор бизнес-правил для начатых или завершённых работ;
- изменение baseline, progress, названий, цветов и прочих несcheduling-полей;
- точное побитовое восстановление исходных дат после последовательности
  `20 → 30 → 20`;
- скрытое исправление циклов, отсутствующих ссылок или некорректных дат.

Первая поставка — только headless API, типы, экспорт, документация и тесты.

## 5. Термины

### Родитель

Задача, на которую ссылается `parentId` хотя бы одного потомка. Родитель не имеет
самостоятельного планового диапазона: его даты всегда выводятся из потомков.

### Листовая работа

Задача без детей. Только листовые работы получают новую собственную длительность.
Даты промежуточных родителей вычисляются после размещения листьев.

### Явный лаг

Значение `dependency.lag` у связи FS/SS/FF/SF. Обычно представляет
технологический разрыв и потому защищено от изменения на первой стадии сжатия.

### Виртуальный лаг

Временное смещение независимой задачи или независимого связанного компонента от
начала выбранного родителя. Оно не записано в `dependency.lag`, но необходимо для
сохранения относительной композиции графика без связей.

### Проектный день

Одна единица длительности в активном режиме:

- календарный день при `businessDays: false`;
- рабочий день при `businessDays: true` с учётом `weekendPredicate`.

Все длительности инклюзивные и должны совпадать с существующей семантикой
`getTaskDuration` и `buildTaskRangeFromStart/End`.

### Минимально достижимая длительность

Наименьший диапазон родителя, который можно получить, не нарушив минимальные
длительности, минимальные лаги, immutable-задачи, календарь и входящие внешние
ограничения.

## 6. Согласованные продуктовые решения

| Вопрос | Решение |
|---|---|
| Семантика родителя | Родитель остаётся вычисляемой обёрткой |
| Основной ввод | Новая длительность родителя |
| Anchor по умолчанию | Сохраняется начало, изменяется конец |
| Единицы | Проектные дни: рабочие или календарные |
| Главный приоритет | Точный общий диапазон |
| Пропорция | Один общий коэффициент для листовых длительностей |
| Сжатие | Сначала длительности, затем положительные лаги |
| Растяжение | Увеличиваются длительности; явные лаги не растут |
| Независимые ветки | Их виртуальные смещения масштабируются |
| Milestone | Длительность остаётся 0, дата масштабируется |
| Locked default | Полностью неподвижна |
| Запрос ниже минимума | Применяется минимум + warning, не hard error |
| Внешние successors | Опциональный каскад без изменения их длительностей |
| Внешние predecessors | Неподвижные входящие ограничения |
| Baseline и progress | Не изменяются |
| Ошибочный граф | Hard error, никаких изменений |
| Обратимость | Детерминированность, но не точное восстановление |

## 7. Пользовательские сценарии

### 7.1 Растяжение связанной цепочки

Исходно родитель занимает 20 рабочих дней. Внутри находятся работы длительностью
4, 6 и 8 дней и два технологических лага по 1 дню. Пользователь вводит 30.

Ожидание:

- начало родителя не меняется;
- явные лаги остаются по 1 дню;
- дополнительные дни распределяются между работами пропорционально их исходным
  длительностям;
- итоговый родитель занимает ровно 30 рабочих дней;
- округление отдельных работ детерминировано.

### 7.2 Сжатие без изменения лагов

Исходно этап занимает 30 дней. Его можно уложить в 24 дня, пропорционально
уменьшив длительности и не опуская их ниже минимумов.

Ожидание: лаги не меняются, диапазон становится ровно 24 дня.

### 7.3 Сжатие после достижения минимальных длительностей

Все работы уже достигли минимальной длительности, но между ними остаются
положительные лаги.

Ожидание: библиотека пропорционально уменьшает разрешённую часть положительных
лагов до `getMinLag`; отрицательные лаги не меняет.

### 7.4 Запрос ниже физического минимума

Пользователь вводит 10 дней, но минимально достижимо 14.

Ожидание:

- применяется график на 14 дней;
- результат имеет `ok: true`, `clamped: true`;
- `requestedDuration === 10`;
- `appliedDuration === 14`;
- присутствует warning `TARGET_CLAMPED_TO_MINIMUM`;
- библиотека не формирует локализованный пользовательский текст.

### 7.5 Независимые параллельные ветки

Две ветки не связаны зависимостями и начинаются в разные моменты внутри этапа.

Ожидание: длительности работ и виртуальные смещения веток масштабируются так,
чтобы сохранить исходную композицию максимально близко и получить точный общий
диапазон.

### 7.6 Locked-задача

Одна из задач locked. Default-политика запрещает менять её положение и
длительность.

Ожидание: остальные работы подстраиваются вокруг неё. Если locked-задача задаёт
нижнюю границу срока, результат clamp-ится к этой границе с warning.

### 7.7 Внешний successor

Задача внутри этапа является predecessor для задачи снаружи.

- В `subtree-only` библиотека не меняет внешнюю задачу и не должна молча оставить
  нарушенную зависимость.
- В `cascade-successors` внешний successor и его транзитивные successors
  сдвигаются существующим cascade-механизмом с сохранением длительностей.

## 8. Публичный API

Рекомендуемое имя:

```ts
scaleTaskSubtreeDuration(
  parentId: string,
  targetDuration: number,
  snapshot: Task[],
  options?: ScaleTaskSubtreeOptions,
): ScaleTaskSubtreeResult
```

Не использовать существующий `resizeTaskWithCascade` как неявную замену. Новая
операция имеет другую семантику: resize одного task range не равен массовому
масштабированию поддерева.

### 8.1 Options

```ts
interface ScaleTaskSubtreeOptions {
  anchor?: 'start' | 'end';
  businessDays?: boolean;
  weekendPredicate?: (date: Date) => boolean;
  externalDependencyPolicy?: 'subtree-only' | 'cascade-successors';
  getMinDuration?: (task: Task) => number;
  getMinLag?: (dependency: TaskDependency, ownerTask: Task) => number;
  isImmutable?: (task: Task) => boolean;
}
```

Defaults:

- `anchor: 'start'`;
- `businessDays: false`;
- `externalDependencyPolicy: 'subtree-only'`;
- обычная листовая работа имеет minimum duration 1;
- milestone имеет minimum duration 0 и всегда остаётся нулевым;
- minimum для положительного lag равен 0;
- отрицательный lag автоматически не изменяется;
- immutable означает `task.locked === true`.

Callbacks должны получать исходные объекты, а не промежуточные клоны. Их значения
нужно вычислить один раз в начале операции, валидировать и сохранить в рабочем
контексте. Нельзя повторно вызывать пользовательский callback внутри итерационного
решателя.

### 8.2 Result

```ts
type ScaleTaskSubtreeResult =
  | {
      ok: true;
      changedTasks: Task[];
      changedIds: string[];
      requestedDuration: number;
      appliedDuration: number;
      clamped: boolean;
      warnings: ScaleTaskSubtreeWarning[];
    }
  | {
      ok: false;
      code:
        | 'INVALID_TARGET_DURATION'
        | 'TASK_NOT_FOUND'
        | 'NOT_A_PARENT'
        | 'INVALID_HIERARCHY'
        | 'INVALID_DEPENDENCIES'
        | 'INVALID_DATES'
        | 'INVALID_MINIMUM'
        | 'EXTERNAL_DEPENDENCY_CONFLICT';
      changedTasks: [];
      changedIds: [];
      details?: string[];
    };
```

Warnings первой версии:

```ts
type ScaleTaskSubtreeWarning =
  | {
      code: 'TARGET_CLAMPED_TO_MINIMUM';
      requestedDuration: number;
      minimumDuration: number;
    };
```

`details` предназначен для диагностики разработчиком. Не помещать туда
локализованные сообщения, секреты или сериализованный snapshot.

## 9. Неподвижные инварианты

Реализация считается неверной, если нарушен хотя бы один инвариант:

1. Входной `snapshot` и вложенные `dependencies` не мутируются.
2. При `ok: false` оба массива изменений пусты.
3. `changedTasks` содержит только реально изменившиеся задачи.
4. `changedIds` совпадает с `changedTasks.map(task => task.id)` и не имеет дублей.
5. Даты родителя равны min/max прямых детей после bottom-up rollup.
6. Изменение вложенного родителя выводится только из потомков.
7. Обычная работа не становится короче своего minimum.
8. Milestone всегда имеет одинаковые `startDate` и `endDate`.
9. Immutable-задача побитово сохраняет scheduling-поля.
10. Явный положительный lag не изменяется, пока целевой срок достижим только через
    изменение длительностей.
11. При растяжении явные lag не увеличиваются.
12. Отрицательные lag не изменяются автоматически.
13. Baseline, progress и несcheduling-поля сохраняются.
14. При достижимой цели `appliedDuration === requestedDuration`.
15. При недостижимом сжатии `appliedDuration` равен доказанному минимуму, а не
    произвольному ближайшему значению.
16. Один и тот же input даёт побитово одинаковый result.
17. Результат проходит dependency validation.

## 10. Валидация до вычислений

Сначала выполнить все проверки, только затем строить рабочий план.

### 10.1 Target

- конечное целое число;
- `targetDuration >= 1` для родительского диапазона;
- дробное, `NaN`, `Infinity`, отрицательное и нулевое значение дают
  `INVALID_TARGET_DURATION`.

### 10.2 Иерархия

- parent существует;
- у него есть хотя бы один потомок;
- `parentId` каждой задачи либо отсутствует, либо указывает на существующую задачу;
- нет self-parent и циклов;
- каждый потомок встречается один раз;
- выбранная область содержит только транзитивных потомков parent.

Обычная листовая задача должна вернуть `NOT_A_PARENT`; для неё остаётся
`resizeTaskWithCascade`.

### 10.3 Даты и календарь

- каждая участвующая дата парсится существующим UTC-safe parser;
- `endDate >= startDate`;
- в business-day mode начало и конец согласуются с существующими правилами
  выравнивания;
- исходный диапазон родителя пересчитывается из детей, а не слепо доверяет его
  сохранённым датам.

### 10.4 Зависимости

- отсутствующие dependency endpoints и dependency cycles дают hard error;
- hierarchy relations не должны создавать неявный dependency edge;
- отдельно классифицировать internal, incoming и outgoing edges;
- зависимости самого родителя являются граничными ограничениями этапа;
- их lag не масштабируется.

### 10.5 Пользовательские минимумы

- duration minimum — целое конечное число >= 0;
- для обычной работы фактический minimum должен быть >= 1;
- для milestone effective minimum принудительно 0;
- lag minimum — конечное целое число;
- minimum положительного lag не может превышать исходный lag;
- некорректный callback result даёт `INVALID_MINIMUM`.

## 11. Внутренняя модель данных

Не изменять `Task` промежуточно. Сначала построить immutable working context:

```ts
interface ScalingNode {
  task: Task;
  depth: number;
  isLeaf: boolean;
  isMilestone: boolean;
  immutable: boolean;
  originalStartIndex: number;
  originalEndIndex: number;
  originalDuration: number;
  minDuration: number;
}
```

Рекомендуемые индексы:

- `0` — фиксированный anchor родителя;
- последующие значения — смещения в проектных днях;
- конвертация index ↔ date использует существующую календарную математику;
- не использовать сырые миллисекунды в business-day mode.

Также построить один индексированный контекст графа, аналогичный существующему
`CascadeContext`:

- task by id;
- children by parent id;
- internal predecessors/successors;
- incoming edges;
- outgoing edges;
- connected component id для каждого листа;
- исходный virtual offset каждого независимого компонента.

Нельзя многократно сканировать полный массив задач внутри внутренних циклов.

## 12. Алгоритм

### 12.1 Общая форма

Операция состоит из пяти чистых фаз:

1. validate and index;
2. derive current normalized layout;
3. solve leaf durations and flexible gaps;
4. materialize dates and roll up parents;
5. validate final graph and create sparse result.

Каждая фаза должна иметь отдельный helper и тестироваться отдельно. Не помещать
всю реализацию в одну функцию.

### 12.2 Нормализация исходного layout

1. Собрать всех потомков выбранного parent.
2. Выделить листья и milestones.
3. Пересчитать диапазоны вложенных родителей от глубоких к корневому.
4. Определить реальный исходный диапазон выбранного parent.
5. Преобразовать даты листьев в project-day indices относительно anchor.
6. Разбить explicit dependency graph на связанные компоненты.
7. Для каждого компонента без входящей внутренней связи сохранить virtual offset
   его начала относительно anchor.

Virtual offset является гибкой частью композиции, но не должен быть записан в
`dependencies`.

### 12.3 Layout evaluator

Нужна чистая функция, принимающая candidate durations, candidate lags и virtual
offsets и возвращающая candidate dates и общий диапазон.

Правила:

- обрабатывать dependency graph в топологическом порядке;
- использовать существующие формулы FS/SS/FF/SF;
- при нескольких predecessors выбирать самое сильное ограничение;
- immutable-задачи сохранять на исходных индексах;
- incoming external dependencies считать неподвижными ограничениями;
- независимый component root ставить по candidate virtual offset;
- дочерние родители не участвуют как duration-bearing nodes;
- после листьев выполнять bottom-up parent rollup.

Evaluator не должен менять lag или duration сам. Он только материализует
переданные кандидаты и сообщает фактический span/conflicts.

### 12.4 Стадия A: длительности

Для всех mutable обычных листьев используется единый коэффициент `k`:

```text
idealDuration[i] = max(minDuration[i], originalDuration[i] * k)
```

Milestones остаются 0. Immutable-задачи сохраняют исходную длительность.

Подбор `k` должен быть монотонным и детерминированным:

- при растяжении `k >= 1`;
- при сжатии сначала искать `0 <= k <= 1`;
- explicit lags на этой стадии неизменны;
- virtual offsets независимых компонентов масштабируются относительно целевого
  диапазона, чтобы их положение не оставалось прибитым к старому масштабу;
- дробные ideal durations переводятся в целые методом largest remainder;
- tie-break: большая дробная часть, затем более ранний original start, затем id.

После округления evaluator определяет фактический span. Если span отличается от
target, выполнить correction pass.

### 12.5 Correction pass для точного диапазона

Точный общий срок важнее идеальной локальной пропорции.

Если span меньше target:

1. найти mutable листья, увеличение которых действительно увеличивает конечную
   границу выбранного parent;
2. распределять остаточные дни в порядке largest-remainder priority;
3. после каждого batch пересчитывать затронутую ветку и итоговый span;
4. не увеличивать explicit lag.

Если span больше target:

1. уменьшать mutable листья на критичных по конечной границе ветках;
2. не переходить minDuration;
3. сохранять максимально близкую общую пропорцию;
4. когда ни одна duration больше не может уменьшить span, перейти к стадии B.

Простой безопасный вариант первой реализации может корректировать по одному
проектному дню с пересчётом evaluator. Он обязан иметь доказанную верхнюю границу
итераций, равную суммарному доступному изменению duration и lag, а не произвольный
magic number. Оптимизацию batch-распределением можно добавить после корректности.

### 12.6 Стадия B: явные и виртуальные лаги

Эта стадия используется только для дальнейшего сжатия.

Порядок:

1. уменьшать положительные internal explicit lags до `getMinLag`;
2. отрицательные lag не изменять;
3. parent-level dependency lags не изменять;
4. уменьшать virtual offsets независимых компонентов до 0 либо до границы,
   заданной incoming constraint/immutable-задачей;
5. распределять уменьшение пропорционально доступному slack;
6. применять deterministic largest-remainder и correction pass.

Если после исчерпания всех регулируемых durations и gaps target всё ещё меньше
span, полученный span является minimumDuration.

### 12.7 Clamp

Clamp — успешный результат, а не ошибка:

```text
requestedDuration < minimumDuration
→ appliedDuration = minimumDuration
→ clamped = true
→ warning TARGET_CLAMPED_TO_MINIMUM
```

Нельзя возвращать исходный snapshot вместо минимального графика. Нужно применить
именно максимально сжатое допустимое положение.

### 12.8 Anchor

`anchor: 'start'`:

- исходная вычисленная дата начала parent фиксируется;
- target end выводится из targetDuration.

`anchor: 'end'`:

- исходная вычисленная дата окончания parent фиксируется;
- target start выводится назад по календарю;
- алгоритм может быть реализован зеркальным преобразованием индексов, но не
  отдельной копией всей scheduling-логики.

### 12.9 Родители

После окончательного размещения листьев:

1. отсортировать родителей по depth descending;
2. каждому присвоить min start/max end прямых детей;
3. не изменять его progress и остальные поля;
4. проверить parent-level dependencies;
5. включить родителя в result только при реальном изменении дат или dependencies.

### 12.10 Внешние связи

#### subtree-only

- никакая внешняя задача не изменяется;
- incoming edges ограничивают новое положение внутренних задач;
- outgoing violation даёт `EXTERNAL_DEPENDENCY_CONFLICT` без изменений;
- результат не может содержать task вне выбранного поддерева и самого parent.

#### cascade-successors

- сначала полностью вычислить поддерево;
- затем применить существующий cascade к внешним транзитивным successors;
- длительности внешних задач сохраняются;
- immutable внешний successor не двигается;
- невозможный внешний cascade даёт hard error и отменяет весь batch;
- каскад не должен возвращаться обратно внутрь поддерева или обрабатывать задачу
  дважды.

## 13. Порядок changedTasks

Для стабильных snapshots и тестов результат должен иметь канонический порядок:

1. изменённые листья поддерева в исходном snapshot order;
2. изменённые родители от глубоких к выбранному parent;
3. внешние cascaded successors в топологическом порядке;
4. без дублей.

Если существующий command-level API требует другой порядок, выбрать один порядок,
зафиксировать его тестом и обновить этот раздел до реализации.

## 14. Архитектурное размещение

Добавить отдельный scheduling-модуль, условно `subtreeScaling`, рядом с hierarchy,
commands, cascade и execute.

Ответственность модулей:

- `subtreeScaling` — validation, solver, allocation, materialization и result;
- `hierarchy` — существующий поиск потомков и rollup primitives;
- `dateMath`/`commands` — project-day conversion и построение диапазонов;
- `dependencies` — существующие формулы типов связей;
- `cascade` — только внешний successor cascade после готового поддерева;
- scheduling types — публичные options/result/warning types;
- scheduling barrel — публичный экспорт.

Не добавлять React, DOM или date-fns в core. Не помещать продуктовые сообщения,
persistence или GetGantt command types в библиотеку.

Перед кодом обязательно:

1. добавить или обновить `MODULE_CONTRACT` нового/затронутых модулей;
2. добавить уникальные semantic blocks для validation, solve durations, solve lags,
   materialize и result;
3. обновить module map/export map;
4. проверить парность и уникальность anchors.

Рекомендуемые anchors:

```text
START_BLOCK_VALIDATE_SCALE_INPUT
START_BLOCK_BUILD_SCALE_CONTEXT
START_BLOCK_SOLVE_DURATIONS
START_BLOCK_SOLVE_FLEXIBLE_GAPS
START_BLOCK_MATERIALIZE_SCALE_RESULT
START_BLOCK_VALIDATE_SCALE_RESULT
```

## 15. Пошаговый план реализации для будущего агента

### Шаг 1. Зафиксировать контракт

- перечитать этот PRD и headless scheduling reference;
- проверить текущие типы `Task`, milestone и dependency;
- обновить `MODULE_CONTRACT` до написания логики;
- создать типы options/result/error/warning;
- не экспортировать функцию до появления тестов базового контракта.

### Шаг 2. Написать красные contract-тесты

Сначала тесты на:

- `TASK_NOT_FOUND`;
- `NOT_A_PARENT`;
- invalid target;
- отсутствие мутации;
- простое `20 → 30`;
- простое `30 → 20`;
- точный appliedDuration.

### Шаг 3. Реализовать validation и indexing

- hierarchy validation;
- dependency validation;
- leaf/parent partition;
- project-day indices;
- internal/incoming/outgoing edge classification;
- cached callback policies.

На этом шаге solver ещё не нужен.

### Шаг 4. Реализовать evaluator

- календарный и business-day режимы;
- все четыре dependency type;
- independent component virtual offsets;
- immutable tasks;
- bottom-up parents.

Проверить evaluator отдельными unit-тестами до allocation logic.

### Шаг 5. Реализовать растяжение

- единый коэффициент durations;
- largest remainder;
- exact-range correction;
- explicit lags неизменны;
- milestone positions изменяются, duration остаётся 0.

### Шаг 6. Реализовать сжатие durations

- общий коэффициент;
- индивидуальные minimum durations;
- locked constraints;
- exact target, когда он достижим без lag changes.

### Шаг 7. Реализовать gap compression и clamp

- positive explicit lags до minima;
- virtual offsets;
- вычисленный physical minimum;
- warning result.

### Шаг 8. Реализовать external policies

- сначала `subtree-only`;
- затем `cascade-successors` через существующие primitives;
- отдельные tests на rollback при конфликте.

### Шаг 9. Sparse result и экспорт

- сравнить итоговые Task с исходными;
- исключить unchanged;
- обеспечить канонический порядок;
- добавить barrel export;
- обновить headless scheduling reference как реализованный API;
- только на этом шаге убрать FUTURE-пометку из документа либо заменить её на
  IMPLEMENTED с указанием версии.

## 16. Обязательная тестовая матрица

### 16.1 Базовая семантика

1. Растяжение последовательной цепочки `20 → 30`.
2. Сжатие последовательной цепочки `30 → 20`.
3. Anchor start сохраняет начало.
4. Anchor end сохраняет конец.
5. Точный requested duration при достижимой цели.
6. Один коэффициент сохраняет порядок относительных длительностей.
7. Largest-remainder tie-break детерминирован.

### 16.2 Минимумы и clamp

8. Обычная работа не становится короче 1 дня по default.
9. Индивидуальный `getMinDuration` соблюдается.
10. После исчерпания durations уменьшаются positive lags.
11. `getMinLag` соблюдается.
12. Negative lag не меняется.
13. Запрос ниже minimum возвращает минимальный график и warning.
14. appliedDuration равен доказанному minimum.

### 16.3 Иерархия

15. Вложенные родители пересчитываются bottom-up.
16. Выбранный parent совпадает с диапазоном потомков.
17. Соседнее поддерево не меняется.
18. Лист возвращает `NOT_A_PARENT`.
19. Missing parent возвращает `TASK_NOT_FOUND`.
20. Hierarchy cycle возвращает hard error без изменений.

### 16.4 Milestones и immutable

21. Milestone перемещается и остаётся нулевым.
22. Locked leaf не меняет ни даты, ни dependencies.
23. Остальные задачи адаптируются вокруг locked leaf.
24. Locked constraint вызывает clamp, если задаёт minimum.
25. `isImmutable: () => false` разрешает изменить locked task.

### 16.5 Связи

26. FS сохраняется и валидна.
27. SS сохраняется и валидна.
28. FF сохраняется и валидна.
29. SF сохраняется и валидна.
30. Multiple predecessors используют strongest constraint.
31. Parent-level dependency lag не меняется.
32. Dependency cycle — hard error, empty changes.
33. Missing endpoint — hard error, empty changes.

### 16.6 Независимые ветки

34. Virtual offset уменьшается при сжатии.
35. Virtual offset увеличивается при растяжении.
36. Параллельные ветки сохраняют относительное расположение максимально близко.
37. Несколько полностью независимых задач дают точный общий диапазон.

### 16.7 Внешние связи

38. Incoming predecessor не меняется.
39. Нарушение outgoing в subtree-only возвращает conflict без изменений.
40. Cascade-successors сдвигает внешнюю цепочку.
41. Внешние durations сохраняются.
42. Immutable внешний successor отменяет атомарную операцию.

### 16.8 Календарь

43. Calendar-day duration совпадает с `getTaskDuration`.
44. Business-day duration совпадает с `getTaskDuration`.
45. Выходные пропускаются через weekendPredicate.
46. Пользовательские рабочие субботы учитываются.
47. Результат не содержит timezone drift.

### 16.9 Атомарность и сохранность данных

48. Deep-freeze input не вызывает mutation error.
49. Dependencies arrays исходного snapshot не изменяются.
50. Baseline сохраняется.
51. Progress сохраняется.
52. Произвольные consumer fields сохраняются.
53. changedTasks sparse и без дублей.
54. Два одинаковых запуска возвращают одинаковый JSON.

### 16.10 Нагрузочный минимум

55. Поддерево из 100 листьев завершается без stack overflow и зависания.
56. Глубокая иерархия не использует небезопасную рекурсию без cycle guard.
57. Iteration bound выводится из регулируемых дней, а не из wall-clock timeout.

## 17. Property-style проверки

Помимо примеров добавить генерируемые либо табличные проверки инвариантов:

- `appliedDuration >= minimumDuration`;
- при достижимой цели `appliedDuration === requestedDuration`;
- каждая mutable ordinary duration >= effective minimum;
- milestone duration === 0;
- immutable scheduling fields unchanged;
- parent range covers every descendant;
- final dependency validation succeeds;
- input deep-equal исходной копии;
- повторный вызов с теми же аргументами deep-equal предыдущему результату.

Не использовать случайность без фиксированного seed.

## 18. Наблюдаемость результата

Core не логирует и не формирует UI-текст. Он возвращает структурированные данные,
достаточные для будущего продукта:

- requested/applied duration;
- clamped flag;
- warning code и minimum duration;
- список реально изменившихся задач;
- hard error code и bounded details.

Будущий GetGantt преобразует warning, например, в сообщение:

> До 10 дней сжать невозможно. Установлен минимально достижимый срок — 14 дней.

Точный UX, канал уведомления и локализация находятся вне этого PRD.

## 19. Критерии приёмки первой реализации

Работа готова только когда одновременно выполнено следующее:

1. Публичный headless API экспортируется из scheduling entry point.
2. Операция не зависит от React, DOM и date-fns.
3. Пример `20 → 30` растягивает поддерево ровно до 30 проектных дней.
4. Достижимое сжатие попадает точно в requested duration.
5. Недостижимое сжатие применяет доказанный minimum и warning.
6. Длительности меняются раньше явных технологических лагов.
7. Явные лаги не растут при растяжении.
8. Независимые ветки масштабируют virtual offsets.
9. Milestones, immutable tasks, parent rollups и external policies работают по
   контракту.
10. Input snapshot не мутируется, result sparse и deterministic.
11. Все новые тесты, полный пакет тестов, build и lint проходят после последних
    изменений.
12. Headless scheduling reference обновлён из FUTURE в фактический API.

## 20. Интеграция GetGantt после стабилизации core

Это отдельная будущая задача. Ожидаемый разрез ответственности:

```text
GetGantt UI
  → пользователь изменяет duration родителя
  → authoritative GetGantt command
  → scaleTaskSubtreeDuration(..., cascade-successors)
  → preview / warning
  → atomic persistence + version + history + Undo + receipt
```

В GetGantt потребуется:

- отдельная команда, а не 100 независимых update-запросов;
- product policy `isImmutable`, вероятно разрешающая менять locked/начатые задачи
  мягче библиотечного default;
- локализованное системное уведомление при clamp;
- preview количества и диапазона изменяемых задач;
- optimistic concurrency и атомарный commit;
- Undo из сохранённого snapshot;
- тесты на server/UI boundary.

До завершения и публикации headless API не начинать product integration.
